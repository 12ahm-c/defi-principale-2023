## 1. الهدف ونموذج الحوكمة الذكية (Purpose & Operating Model)

### 1.1 الهدف
يحدد هذا الدليل قواعد التشغيل والضبط المنهجي الصارم لاستخدام **وكلاء الذكاء الاصطناعي (AI Agents)** في تنفيذ وصيانة واختبار مشروع «كاميرا الحقيقة». يهدف النظام إلى ضمان:
* منع أي هلوسة أو اختراع لمعلومات مناخية زائفة أو نسب أرقام لغير مصادرها المعتمدة.
* الالتزام الصارم بالهيكل والتنظيم الوارد في `cahier_charge.md` (الشاشات الست، التدفق الخطي، قيد الادعاء الواحد، وعدم إشعار الذنب).
* الالتزام الحصري بالمحتوى الفعلي المستخرج من `Ressources.md`.
* منع تسرّب أي مفاهيم أو تقنيات من المشروع السابق (`fichiers principales/`).

### 1.2 نموذج التشغيل الثلاثي (Triad Operating Model)
تعتمد الحوكمة على دورة ثلاثية منضبطة تضمن الفصل التام بين التخطيط، والتنفيذ، والتدقيق المستقل:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        1. AI ORCHESTRATOR                              │
│         (تحميل السياق، تحديد النطاق، فحص التبعيات، وتعيين المهام)         │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │
                                   │ تكليف بنطاق محدد ومغلق
                                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│                          2. AI BUILD AGENT                             │
│         (التنفيذ البرمجي فقط داخل الملفات المصرح بها ومطابقة العقود)       │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │
                                   │ تسليم المخرجات للفحص المستقل
                                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│                      3. AI VERIFICATION AGENT                          │
│     (تدقيق مستقل للقراءة فقط مقابل cahier_charge.md و Ressources.md)   │
│             تقرير تدقيق إلزامي: [PASS / PASS WITH NOTES / FAIL]        │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │
                    ┌──────────────┴──────────────┐
                    ▼                             ▼
              [حالة FAIL]                   [حالة PASS]
        (إعادة فورية للتصحيح)         (اعتماد واكتمال المرحلة)
```

## 3. أدوار ومسؤوليات وكلاء الذكاء الاصطناعي (AI Agent Roles)

### 3.1 وكيل التنسيق والتوجيه (AI Orchestrator)
* **المسؤولية**:
  - قراءة `master-plan.md` وتحديد المرحلة الحالية (من 1 إلى 6).
  - تحديد الملفات المصرح بتعديلها والملفات المحظورة بدقة قبل بدء العمل.
  - ضمان عدم الانتقال لمرحلة تالية إلا بعد حصول المرحلة السابقة على ختم `PASS` من وكيل التحقق.
  - إيقاف أي مهمة فوراً إذا طلبت إضافة شاشات جديدة، أو تسجيل دخول، أو قواعد بيانات خارجية.

### 3.2 وكيل البناء والتنفيذ (AI Build Agent)
* **المسؤولية**:
  - تنفيذ الكود أو الوثائق المطلوبة داخل النطاق المصرح به حصراً.
  - الالتزام التام بـ `api-contract.md` (المسارات، كائنات DTO، ورموز الحالة).
  - الالتزام بالحياد العلمي وعدم لوم المستخدم إطلاقاً في الواجهات أو النصوص.
  - التوقف الفوري عند الحاجة لملف خارج النطاق وطلب إذن المنسق (Orchestrator).

### 3.3 وكيل التحقق والتدقيق المستقل (AI Verification Agent)
* **المسؤولية**:
  - العمل كـ **وكيل تدقيق مستقل (Read-Only Auditor)** لا يعدل أي ملف بنفسه.
  - يُستدعى تلقائياً بعد انتهاء أي مرحلة من المراحل أو عند تعديل أي ملف في `new files/`.
  - مراجعة الملف المنتَج مقابل `cahier_charge.md` و `Ressources.md` وفق المحاور الأربعة:
    1. التحقق مقابل الهيكل (`cahier_charge.md`).
    2. التحقق مقابل المحتوى (`Ressources.md`).
    3. التحقق من الاتساق الداخلي مع ملفات `new files/` السابقة.
    4. التحقق من عدم تسرّب أي مفاهيم من المشروع السابق (`fichiers principales/`).
  - إصدار **تقرير التحقق (Verification Report)** بحكم قاطع: (`PASS` / `PASS WITH NOTES` / `FAIL`).

## 4. بروتوكول تحميل السياق حسب طبيعة المهمة (Context Loading Protocol)

لمنع تشتت الذاكرة وضمان دقة الاستجابة، يلتزم الوكلاء بقواعد تحميل السياق التالية:

| نوع المهمة المكلف بها الوكيل | المصادر الإلزامية التي يجب تحميلها وقراءتها أولاً | المصادر الممنوع تحميلها لمنع التشتت |
| :--- | :--- | :--- |
| **مهمة في الهيكل وتدفق الشاشات** | `cahier_charge.md` + `new files/architecture.md` + `new files/frontend-plan.md` | ملفات المشروع السابق `fichiers principales/*` |
| **مهمة في بيانات وتقييم ادعاء** | `Ressources.md` + `new files/api-contract.md` + `src/data/claims.json` | أي مصادر إنترنت عامة غير موثقة |
| **مهمة في مسارات 2050** | `Ressources.md` (قسم Transitions 2050) + `new files/architecture.md` | افتراضات تنبؤية خارج سيناريوهات ADEME الأربعة |
| **مهمة في البنية التحتية والنشر**| `cahier_charge.md` (قسم الالتزامات) + `new files/infra-plan.md` | وثيقة `infra-plan.md` للمشروع السابق |
| **مهمة تدقيق واختبار شامل** | كافة ملفات `new files/` + `cahier_charge.md` + `Ressources.md` + `AGENTS.md` | - |

## 5. قواعد العمل الصارمة لوكيل البناء (Build Agent Guardrails)

### 5.1 قائمة الأوامر المحظورة قطعيًا (Strict Prohibitions)
يُحظر على وكيل البناء والذكاء الاصطناعي تحت أي ظرف:
1. ❌ **حظر إضافة تسجيل دخول**: منع إنشاء نماذج دخول، كلمات مرور، رموز JWT، أو إدارة جلسات معقدة (الالتزام بـ Zero-Auth).
2. ❌ **حظر قواعد البيانات والخوادم الخارجية**: منع استخدام MongoDB، PostgreSQL، Redis، خوادم Socket.IO، أو مهام Cron.
3. ❌ **حظر استخدام كاميرا العتاد الحقيقية**: الالتزام الحاسم بمحاكاة الكاميرا بـ CSS النقي فقط (`No navigator.mediaDevices`).
4. ❌ **حظر عرض أكثر من ادعاء واحد**: الالتزام الصارم بـ: «ادعاء واحد فقط في كل لحظة عبر جميع الشاشات»، ومنع عرض ادعاءين معاً في الشاشة 4.
5. ❌ **حظر الرسوميات الثقيلة**: منع استخدام WebGL أو مكتبات ثلاثية الأبعاد؛ الاكتفاء بانتقالات CSS البسيطة (≤ 300ms).
6. ❌ **حظر لوم المستخدم**: منع أي رسائل إشعار بالذنب؛ الجبل الجليدي يعكس سلامة المعلومة لا أخلاق الفرد، وزر «التالي» متاح دوماً.
7. ❌ **حظر اختراع المصادر**: حظر استدعاء أو فبركة مصادر أو دراسات خارج المصادر العشرة المعتمدة في `Ressources.md`.
8. ❌ **حظر التكذيب في غياب الدليل**: تطبيق قاعدة الـ Fallback المحايدة بدقة: *«لم نتمكن من التحقق من هذه الصياغة من المصادر المعروضة»* عند نقص الدليل دون تكذيب.

## 6. بروتوكول التدقيق الصارم لوكيل التحقق (Verification Agent Protocol)

تطبيقاً لقواعد ملف `AGENTS.md` الصارمة:
1. **الاستقلالية التامة**: لا يقوم وكيل التحقق بكتابة الكود أو تعديل الملفات إطلاقاً.
2. **إسناد المخالفات**: كل مخالفة يجب أن تُسند بنص صريح إلى فقرة محددة في `cahier_charge.md` أو عنصر في `Ressources.md`.
3. **الفصل بين الهيكل والمحتوى**:
   - مخالفة هيكلية ← تقاس مقابل `cahier_charge.md`.
   - مخالفة محتوى ← تقاس مقابل `Ressources.md`.
4. **التعامل مع الشك**: عند الشك في نقطة معينة، تُصنف كـ **Open Question** ولا تُعتبر مخالفة قطعية.
5. **صيغة التقرير الإلزامية**: يُصدر الوكيل تقريره وفق الهيكل المحدد في `AGENTS.md`:
   - الحكم العام (`PASS` / `PASS WITH NOTES` / `FAIL`).
   - جدول المخالفات المفصل (إن وُجدت).
   - المخالفات حسب النوع (هيكل، محتوى، اتساق، تسرب).
   - تقييم الافتراضات والمسائل المفتوحة.

## 7. قواعد مكافحة الهلوسة والنزاهة العلمية (Anti-Hallucination & Scientific Integrity)

لحماية المحتوى العلمي للمشروع، يتبع وكلاء الذكاء الاصطناعي بروتوكول مكافحة الهلوسة التالي:

```
[ مصادفة ادعاء أو رقم أو سؤال أثناء العمل ]
                     │
                     ▼
[ هل النص أو الرقم موجود صراحة في Ressources.md؟ ]
        │                               │
       نعم                              لا
        │                               │
        ▼                               ▼
[ تضمينه مع ذكر المصدر ]       [ هل يمكن استنتاجه منطقياً بيقين تام؟ ]
[ والصفحة والرابط المحدد ]             │                   │
                                      نعم                  لا
                                       │                   │
                                       ▼                   ▼
                          [ توثيقه كـ Assumption صريحة ] [ إيقاف الاستنتاج وتفعيل ]
                          [ مع الإشارة للمصدر المقارب  ] [ قاعدة Fallback المحايدة: ]
                                                       [ «لم نتمكن من التحقق...» ]
```

### 7.1 قيود المصادر العشرة الواجب احترامها برمجياً
* **IPCC (AR6)**: التمييز بين الرصد التاريخي والتوقعات المشروطة؛ إبقاء أرقام ما قبل COP26 مؤرخة دون تقديمها كأرقام راهنة.
* **ADEME**: عزو كل رقم لدراسته وصفحته؛ منع تعميم المؤشرات والنسب الفرنسية على مستوى العالم.
* **Transitions 2050**: عرض المسارات الأربعة كنماذج استشرافية مشروطة بفرضيات محددة، وحظر تقديمها كقياس حالي أو تنبؤ حتمي.
* **Réseau Action Climat**: التمييز الصريح بين خلاصات IPCC العلمية ومقترحات الشبكة السياسية؛ التركيز على الحلول الداعمة وتجنب لوم الأفراد.
* **Nos Gestes Climat & Climate Q&A**: تقديم المحاكي كأداة تقدير تقريبية، و Climate Q&A كنموذج استرجاع فقرات يتطلب فحص النص الأصلي.
* **HCC, CNED, Bon Pote**: استخدام بطاقات حجج التقاعس لطرح أسئلة متابعة واستيضاح فقط، وحظر استخدامها للحكم بكذب الادعاء.

## 8. بوابات التحقق ونقاط التصعيد الحرجة (Validation Gates & Escalation Triggers)

يجب على الوكيل **التوقف الفوري والتصعيد للمستخدم البشري (Escalate to Human User)** في الحالات التالية:
1. إذا طُلب منه إضافة شاشة سابعة أو تعديل التتابع الخطي للشاشات الست.
2. إذا طُلب منه تثبيت أو دمج أي واجهة برمجية خارجية حية (External Live API).
3. إذا تعذر العثور على سند لادعاء مناخي جديد في مصادر `Ressources.md`.
4. إذا طُلب منه تغيير صيغة بطاقة التحقق الرباعية أو تجاوز قاعدة Fallback المحايدة.
5. إذا صدر حكم `FAIL` من وكيل التحقق (يُمنع تجاوز الـ Gate والانتقال للمرحلة التالية قبل الإصلاح).

## 9. قوالب توجيه الوكلاء (Prompt Templates for AI Agents)

### 9.1 قالب تكليف وكيل البناء (Build Task Prompt)

```markdown
# TASK ASSIGNMENT: [اسم المهمة]
- المرحلة الحالية: Phase [1–6] من master-plan.md
- نوع المهمة: [Data | UI Component | Core Service | Test | Deployment]

## المصادر الإلزامية للقراءة قبل البدء:
1. cahier_charge.md (الشاشات، التدفق، قيد الادعاء الواحد، وعدم اللوم)
2. Ressources.md (المصادر المعتمدة وحدودها ومحتوى الادعاء)
3. new files/architecture.md & new files/api-contract.md
4. [frontend-plan.md أو backend-plan.md حسب الاختصاص]

## النطاق المصرح به:
- الملفات المسموح بإنشائها أو تعديلها: [قائمة المسارات]
- الملفات المحظورة: [كافة الملفات خارج النطاق]

## القواعد الصارمة:
- ادعاء واحد فقط في كل لحظة.
- لا تسجيل دخول، لا قواعد بيانات، لا كاميرا عتادية، لا APIs خارجية.
- تفعيل Fallback المحايد: «لم نتمكن من التحقق من هذه الصياغة من المصادر المعروضة» عند نقص الدليل.
- مطابقة تامة لـ API Contract وقالب { success, data, error, meta }.

## معايير القبول (DoD):
- [قائمة بنود التحقق من master-plan.md للمرحلة الحالية]
```

### 9.2 قالب استدعاء وكيل التحقق (Verification Audit Prompt)

```markdown
# VERIFICATION AUDIT REQUEST
- المرحلة المنتهية: Phase [X]
- الملف المنتَج للمراجعة: new files/[filename.md]

## التعليمات الإلزامية للوكيل:
1. اقرأ ملف AGENTS.md والتزم بصفة المدقق المستقل للقراءة فقط (Read-Only).
2. اقرأ cahier_charge.md بالكامل للتحقق من الهيكل والتنظيم.
3. اقرأ Ressources.md بالكامل للتحقق من صحة المحتوى الفعلي.
4. اقرأ ملفات new files/ السابقة للتحقق من الاتساق الداخلي.
5. تحقق من خلو الملف كلياً من أي تسرّب لمشروع ShopManager السابق.

## المخرج المطلوب:
- إصدار تقرير التحقق المعتمد (Verification Report) متضمناً:
  1. الحكم العام الصريح: [PASS / PASS WITH NOTES / FAIL]
  2. جدول المخالفات (إن وجدت) مسندة للمراجع بدقة.
  3. التحقق حسب المحاور (أ، ب، ج، د).
  4. الافتراضات والمسائل المفتوحة.
```

## 10. مصفوفة الامتثال والتسليم النهائي (Master AI Compliance Matrix)

| المتطلب الجوهري للنظام | آلية الضبط في الـ AI Workflow | حالة الضمان |
| :--- | :--- | :--- |
| **الشاشات الست وتدفقها الخطي** | منع إنشاء أي مسارات أو شاشات خارج الشاشات 1 إلى 6 | ✅ مضمون 100% |
| **ادعاء واحد فقط في كل لحظة** | حظر برمجيات العرض المتزامن وتأمين التتابع الفردي في الشاشة 4 | ✅ مضمون 100% |
| **محاكاة الكاميرا بـ CSS فقط** | منع استدعاء عتاد الكاميرا أو استخدام WebGL | ✅ مضمون 100% |
